# YRSS evaluation v3 pre-registration

Date: 2026-11-17. The owner approved a follow-up study for a JCSSE 2027 paper
and a course manuscript. This record is that approval, written before any v3
training run and before the test-v3 split is sealed. Version: `yrss-eval-v3`.
Code: `benchmark/yrss_v3/`.

It does not rescore, reopen, or decrypt the v2 test split. v2 was scored once.
The score files are `research/yrss2026/v2/RESULTS.md`,
`research/yrss2026/v2/test-nonllm.json`, and
`research/yrss2026/v2/test-llm-typhoon4b-seed1.json` through `seed5`. The seal
is `benchmark/data/yrss-v2/test.lock.json` under
`docs/decisions/2026-11-13-yrss-eval-v2.md`. Those numbers are secondary
evidence. They are not a primary endpoint of this study, and this study does
not run v2 again.

## Why a new split

v2's test split has already been scored, so it cannot be the unseen test for
a new fine-tune. The new questions also need quasi-identifier labels and more
than one operating point. Those labels are not in the v2 scheme.

## Research questions

WP1. On documents from the v3 test families, what are the per-type precision,
recall, and F2 of fine-tuned WangchanBERTa-style and PhayaThaiBERT-style
encoders, compared with the baselines named below?

WP2. On the same documents, how do the three operating points of the
fail-closed hybrid stack trade per-type F2, over-redaction rate, and latency?

WP3. After redaction at each operating point, what fraction of documents have
a residual quasi-identifier combination that occurs fewer than k times in a
separate synthetic population, and what is TRIR per Section 26 category?

The paper and the course manuscript share this one test. They may both quote
the single score. Neither may score the split on its own.

## Systems and fine-tuning

Training text is synthetic. It comes only from the v3 train families. The dev
families are for early stopping, threshold choice, and error inventory. Test
families are not used for weights, stopping, or thresholds.

External data, including Meddies-PII, which the approval describes as
CC BY-NC, is an optional ablation only. No file in this repository vendors

families. A hit blocks that ablation. The licence review for a download is
TBD and has to be recorded before the download. Value-level collision with
the shared generators in `benchmark/yrss_v2/values.py` is not what that check
measures. A value-level check is TBD.

Label scheme for the fine-tune: the eleven types in
`benchmark/yrss_v2/types.py` (`SCHEME_TYPES`). DRIVER_LICENSE stays in place of
STUDENT_ID, as in the v2 record. Quasi-identifiers are not NER training labels.
Optimizer, learning rate, epochs, batch size, and maximum length are TBD.
They are frozen in an addendum before the first training step of that system.

No paid API and no hosted model is called for training or for the test score
unless the owner approves that call in writing. This approval does not.

## Corpus

Synthetic only. No real person's data is collected, searched for, or copied.
Public place names and form-like wording may appear. Every value is generated.

Families live in `benchmark/yrss_v3/families.py`. A family id starts with
`v3-train-`, `v3-dev-`, or `v3-test-` and stays in that split. Splits do not
share a family. Fixed text is also checked against the committed v2 dev
templates at `benchmark/data/yrss-v2/dev-templates.jsonl`, using the Jaccard
threshold `NEAR_DUPLICATE_JACCARD` in `benchmark/yrss_v2/corpus.py`. The sealed
v2 test is not opened, so overlap with its wording is not byte-checked. The
v3 families were written for this record and are not copies of the v2 dev lines.

Seeds and variants are `SEEDS` and `VARIANTS` in `benchmark/yrss_v3/corpus.py`:

| Split | Seed | Variants per family |
|---|---:|---:|
| train | 20261117 | 2 |
| dev | 20261118 | 2 |
| test | 20261119 | 2 |

Test values also mix in a fingerprint of the key, so the public seed does not
rebuild the sealed documents. Train and dev do not take a key. Rendering always
uses the v2 strict digit rule: Thai digits are not mixed into a value that
contains Latin letters (`benchmark/yrss_v2/corpus.py`, the strict path).

Domains in each split: clinical notes, government forms, chat, and insurance,
plus one notice family with decoys and no personal placeholders. Counts of
documents, entities, and Section 26 labels for train and dev are the lock
files `benchmark/data/yrss-v3/train.lock.json` and
`benchmark/data/yrss-v3/dev.lock.json`. This record does not copy those counts.
The test lock does not exist yet. Its counts are TBD until the key holder seals.
Changing the family lists after this record is an addendum, and that addendum
has to land before the seal. The inventory in `families.py` at the seal commit
is the one the ciphertext freezes.

Gold entity spans come from the placeholders. They are not the output of a
detector. This change does not edit `pii_redactor/` detectors.

### What is public before the seal

Test family wording is in `families.py`, so sealing does not need a second
authoring pass. That is a weaker blind than v2, where the test templates were
not in the tree. Filled test documents are not public: they are drawn with the
key and stored only as ciphertext. Reading the test templates to choose a
model, a threshold, or a training example spends the split.

## Seal

The key holder generates a key outside the repository with
`benchmark.blind.generate_key`, then seals with one command. The variable is
a path to the key file, the same pattern as `YRSS_V2_TEST_KEY_FILE`. The key
is not an argument, not a default path, and not printed.

```
YRSS_V3_TEST_KEY_FILE=/path/to/keyfile python -m benchmark.yrss_v3 seal
```

The path must be outside every git work tree. The command refuses a key file
inside one. It writes `benchmark/data/yrss-v3-test.enc` and
`benchmark/data/yrss-v3/test.lock.json`. It does not write a plaintext test
file. There is no overwrite. The ciphertext is the rendered documents
(`canonical_bytes`), authenticated with the existing blinding helper in
`benchmark/blind.py`. The threat model is the one in that file: blinding
against accidental reading, not secrecy against someone who has the key.

`python -m benchmark.yrss_v3 verify` checks `ciphertext_sha256` and the lock
schema. It does not decrypt and it does not read the key. Until the key holder
commits those two files, verify reports `not-sealed`. That is the expected
state of this change. CI can run verify on a sealed tree without the key.

After the seal, the ciphertext is the test corpus. Editing `families.py` does
not change documents that were already sealed.

## Quasi-identifiers (WP3)

Placeholders in `benchmark/yrss_v3/qi.py` (`QI_KINDS`): nickname, abbreviated
address, Thai Buddhist-era date, age, occupation, and one placeholder for each
code in `pii_redactor/pdpa_categories.py` (`SECTION26_CATEGORIES`). A code is
attached only where `QI_KINDS` maps the placeholder to that code. Nickname,
abbreviated address, Buddhist-era date, age, and occupation are quasi-identifiers
with no Section 26 code.

The ontology record
`packages/amphrang/docs/decisions/2026-08-26-pdpa-data-ontology.md` lists the
statute's race and ethnic-origin phrases and stores them as the one code
`RACE_ETHNICITY`. This study does not add, split, or drop a code. Unresolved:
the approval text said an 11-category catalog; the code tuple is what this
study reports. An addendum may say otherwise before scoring. It may not invent
a code that the tuple does not contain.

Nicknames and abbreviated addresses are not gold `NAME` or `ADDRESS` spans. A
system that labels them as those types takes a false positive on the
eleven-type view, which is the v2 unrestricted rule.

### Document-level risk

k is `K_ANONYMITY` in `benchmark/yrss_v3/protocol.py`, value 5, from this
approval. The population is a separate synthetic background. Its size is TBD.
`synthetic_population` takes the size from the caller and has no registered
default. The evaluated document is not inserted into the population before
the count.

The key of a document is the sorted set of residual `(qi_type, surface)`
pairs. That joint key is the co-occurrence. Marginal uniqueness of one field
is not the registered metric. A quasi-identifier remains residual unless every
one of its characters sits inside some redacted span. A document with no
residual quasi-identifier is not risky. A document is risky when the
population count of its key is less than k. `risk_rate` divides the risky
documents by every document.

TRIR is secondary. `trir_by_section26` only aggregates outcomes the caller
supplies, one rate per catalog code. The attacker is TBD. An empty category
is a null rate, not a zero. No attacker is implemented in this change, and no
TRIR number is claimed.

## Metrics

- Per-type precision, recall, and F2 on the eleven types, type-aware overlap,
  one gold span to at most one prediction, via `benchmark/blind_v2/score.py`
  unchanged. `benchmark/yrss_v3/metrics.py` is the wrapper.
- Micro F2 is the summary used for paired tests, as in v2. Per-type rows are
  reported and are not each a Holm test.
- Over-redaction rate: characters outside gold entity spans that a prediction
  covers, divided by the characters outside those spans. No pass/fail cutoff
  is registered (TBD).
- Latency: warm per-document time, reported as a descriptive secondary the
  way the v2 record's latency line is descriptive. No budget is registered
  (TBD). No latency number is produced by this change.
- WP3 document risk as defined above. TRIR per Section 26 code, secondary.

## Significance

The same procedure as v2, implemented in `benchmark/yrss_v2/stats.py` and
called from `benchmark/yrss_v3/stats.py`:

- Family cluster bootstrap, not document bootstrap. `N_RESAMPLES` and `SEED`
  in `benchmark/yrss_v2/stats.py`. Intervals are the 95% percentile intervals
  from that module.
- Paired difference of micro F2, same resamples.
- Holm step-down, family alpha 0.05, the alpha written in the v2 record.
  Membership of the Holm family is TBD until the runnable system list and the
  operating-point thresholds are frozen. That addendum comes before any test
  score. A system that cannot be run is dropped there, not after seeing a
  p-value.
- Approximate randomization: paired sign-flip of the same family aggregates
  (`sign_flip_difference`). The permutation count is `N_PERMUTATIONS`, set
  equal to `N_RESAMPLES`, same seed. Holm uses the same function. The
  sign-flip is reported beside the bootstrap. It does not replace it.

An interval that includes zero is reported as no demonstrated difference.
Null and negative results are reported.

## Operating points

Three names, and no numeric thresholds: `recall-first`, `balanced`,
`precision-first` (`OPERATING_POINTS` in `benchmark/yrss_v3/protocol.py`).
The thresholds are fit only on train and dev and written into an addendum
before the test seal is scored. They are TBD in this record.

The hybrid stack is the existing fail-closed core. Outbound findings become a
fail-closed decision (`pii_redactor/leak_guard.py`, `scan_residual_signals`).
Section 26 stays a warn/report signal, not an automatic block, which is the
product rule. This pre-registration does not change that code. Which frozen
WP1 model, if any, sits inside the hybrid is TBD in the freeze addendum. The
product default is not silently one of the three points unless that addendum
says so.

## Stopping rules

1. The test split is sealed before any training run that this study will
   report. A training run started before the ciphertext and the lock exist is
   not part of this pre-registration.
2. The test-v3 split is scored exactly once, after every system, every
   revision pin, and every operating-point threshold is frozen. `TEST_SCORES_ALLOWED`
   in `benchmark/yrss_v3/protocol.py` is 1.
3. No per-document test text, test value, or intermediate candidate is
   disclosed before that run. After it, nothing is tuned on this split.
4. v2 is not scored again. Quoting its published files is allowed only as
   secondary evidence, with the v2 label kept on those numbers.
5. A detector or model change after the v3 score spends the split. A new
   hypothesis needs a new record and a new test split.
6. A failed integrity check (`verify` or the plaintext hash on open) is a
   failed evaluation.
7. An external ablation that fails the contamination check is not run.

## What this will and will not support

It supports a claim about these constructed Thai documents, a comparison of
the registered systems on them, and a document-level uniqueness rate under
the stated k and the stated population. It does not support real-document
accuracy, legal compliance, anonymity, or a population risk for Thailand.
The population is synthetic. TRIR, once an attacker exists, is a property of
that attacker.
